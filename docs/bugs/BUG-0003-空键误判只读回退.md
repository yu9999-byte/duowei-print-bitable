<title>BUG-0003 — 飞书空键误判为损坏模板集合</title>

- 状态：已关闭（正式新建、保存、重开及多模板目录通过）
- 日期：2026-09-24
- 关联：SPEC-SAVE-01/04、ADR-0009、PHASE-02F

# 现象与证据

正式 Base `PO-0001`、应用 `1.0.8` / 小组件 `1.0.10` 的新版工作台显示“0 个模板 / 只读回退”，警告“模板集合存储格式无效或引擎版本不兼容”，新建模板被禁用。前台打印预览能显示当前记录真实值，故数据和预览链路与模板存储故障须分开判断。

在该插件 iframe 中只读调用 `bitable.bridge.getData`，v2 集合键、base/table v1 键、table-only v1 键及额外无关键均返回空普通对象 `{}`（只检查类型/键名，无模板正文读取或存储写入）。仓库原先仅把 `null/undefined` 判作缺失键，因此把 `{}` 送入 v2 解析并进入只读回退。

# 修复与边界

TDD：新增空键与非空未知对象回归，Red 为 `readCollection` 报格式错误；仓库读取边界只把空普通对象视作无值，三个键一致处理。非空未知、未来版本或校验失败仍拒绝覆盖。目标是允许首次新建并保存，不改变已有非空旧模板。

bridge 无法区分真正存入的 `{}` 与不存在的键；合法模板从不以空对象存储。这是宿主返回约定的适配，并非通用损坏数据自动修复。灰度版本发布后须验证首次保存、关闭重开、两个模板及旧模板读取；未通过前不得关单。

2026-09-24：小组件 `1.0.11` / 应用 `1.0.9` 已灰度至 `F225904757`，正式 Base 的插件脚本 `main.175f67dc.js` 与修复构建一致。后续包含本修复的组件 `1.0.13` / 应用 `1.0.10` 已再次灰度；这只证明发布链路更新，不替代首次新建和重开 E2E。宿主记录面板曾出现“服务器繁忙”；刷新后 iframe 已加载，但跨域画面截图超时，首次新建与重开仍未取得证据。本问题保持开放。

# 关闭证据（2026-10-07）

后续正式验收已连续使用由产品入口创建并持久化的“新模板 2”“标签模板 3”“连续模板 4”“标签模板 5”。其中“新模板 2”经历编辑、保存、返回预览、切换模板、重新打开、跨记录重新解析和 PDF 输出；Goal v7 正式版本再次读取到 5 个模板，目录可选择且唯一“新建模板”入口可用，没有再进入“0 个模板 / 只读回退”。这证明空键首次初始化后的新建、集合保存和后续重开链路已经实际工作。非空未知对象、跨用户并发、只读权限和容量仍属于模板仓库的独立边界，不再作为 BUG-0003 保持开放的理由。
