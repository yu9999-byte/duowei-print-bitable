<title>PHASE-09 — 批量容量与异常恢复闭环</title>

# 目标

把现有“3/10 条正式可用、50 条隔离输出通过”的批量能力推进到事务级 50/51 边界和同批次超时重试，三种排版共享同一可靠性合同。

# 启动审计

- 已有：50 条网关读取并发上限 4、顺序保持；51 条 session commit 拒绝；读取超时、停止派发、旧批次保留、迟到响应隔离的自动化；默认 50 页隔离引擎输出。
- 缺口一：App 在 `loadPrintJob` 前检查 51 条，但候选事务本身在 load 后才拒绝，无法证明所有调用路径均“读取前拒绝”。
- 缺口二：超时后的“重试批量读取”再次调用普通选数流程，未冻结原 Base/表/视图/模板/记录集合，不符合按钮语义。
- 正式业务 Base 只有 10 条，不修改业务数据凑 50/51 证据。独立受控测试 Base 写入和后续发布仍需单独授权。

# TDD 顺序

1. Red：事务 51 条调用 loader；重试请求不存在或可被调用方改写；App 重试仍打开选择器。
2. Green：事务前置校验、请求/结果一致性、不可变重试快照、同快照重试和上下文失效。
3. Refactor：删除 App 重复的唯一安全责任，统一三模式入口；保留即时友好提示。
4. 回归：全量测试、构建、真实设计器 50 条压力门、`git diff --check`。
5. 正式：另获授权后，仅在独立测试 Base 使用虚构 1/10/50/51 条；上传与灰度另行确认。

# Red → Green 结果

- Red：`UT-BATCH-12` 实测 51 条仍调用一次 loader；`UT-BATCH-13` 因重试快照模块不存在失败；`CT-BATCH-11-UI` 证明按钮仍调用 `requestLoadRecords(true)`，会重新打开选择器。
- Green：`validateBatchRecordIds` 下沉到候选事务入口；loader 只能收到已校验有序 ID，返回缺项或乱序均在 render 前拒绝。
- Green：新增只存在于内存且冻结的 `BatchRetryRequest`。超时保存 Base/表/视图/宿主记录、模板和有序记录 ID；点击重试直接重放，不进入 `selectRecordIds`。上下文或模板改变时快照清除或拒绝。
- Green：普通重新选择、退出批量、重载上下文和候选成功都会清理旧快照；非超时失败不显示误导性重试。
- Green：默认、连续、标签仍只调用一次 `prepareBatchCandidate`，布局仅在同一 render 回调分流，共用容量和异常恢复规则。
